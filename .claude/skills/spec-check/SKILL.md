# Сверка с ТЗ

Подход адаптирован из методики spec-to-code compliance (Trail of Bits): каждое требование проверяется отдельно, вердикт подкрепляется конкретными строками кода, а не названиями функций.

Эталон: `docs/spec/tz.md`. Принятые уточнения: `docs/PROJECT_CONTEXT.md` → «Решения» (они имеют приоритет над ТЗ, если явно его меняют).

## Шаги

1. **Область.** Уточни, что проверяем: весь продукт, модуль (например, «Расписание и правила ставок») или конкретный PR.
2. **Реестр требований.** Разбей нужные разделы ТЗ на атомарные, проверяемые требования и веди их в `docs/spec/requirements.md` с ID (`AUC-01`, `PAY-03`, …). Если файл уже есть — используй его ID, новые требования добавляй в конец. Одно требование = одно проверяемое утверждение («ставка в 18:00 отклоняется»), а не абзац.
3. **Проверка каждого требования.** Для каждого:
   - где это должно быть обеспечено (модуль, сервис, guard, миграция, UI);
   - прочитать саму реализацию **и** её вызовы — обеспечено ли на *всех* путях (HTTP, WebSocket, фоновая задача, админка);
   - есть ли тест, который это проверяет (ссылка на файл);
   - вердикт + доказательство (`файл:строка`) или, для `absent`, какие поиски выполнены (паттерны grep и где).
   Большой объём (> ~10 требований) — раздели на подагентов по разделам ТЗ, каждый со своим списком ID; итог собирай сам.
4. **Обратное направление.** Что код делает, чего нет в ТЗ (лишние эндпоинты, правила, поля с ПДн)? Это тоже находки.
5. **Попытка опровергнуть.** Перед тем как записать `contradicted`/`partial`/`absent`, перечитай код ещё раз с целью найти, где требование всё-таки обеспечено (базовый guard, триггер, constraint в БД, вызывающий код).
6. **Отчёт** в `docs/spec/compliance-report.md` (перезаписывается) и краткое резюме пользователю.

## Вердикты

| Вердикт | Значение |
|---|---|
| `implemented` | Обеспечено на всех путях, есть тест |
| `partial` | Работает на основном пути, но есть путь в обход (часто самое опасное) |
| `contradicted` | Код делает иначе, чем ТЗ |
| `stronger` | Код строже ТЗ — недокументированное ограничение |
| `absent` | Не найдено (с перечнем выполненных поисков) |
| `undecidable` | ТЗ слишком расплывчато, чтобы проверить → вопрос к заказчику |
| `deferred` | Вне MVP по зафиксированному решению (ссылка на решение) |

## Серьёзность

- **Critical** — деньги/доступ двигаются так, как ТЗ запрещает, и это может вызвать посторонний (двойной допуск, ставка без допуска, утечка ПДн).
- **High** — то же, но нужен особый доступ или редкое состояние; или защита есть везде, кроме одного достижимого пути.
- **Medium** — реальный разрыв с неочевидным последствием.
- **Low** — поведение верное, неточна документация. Исправлять документ.

## Формат отчёта

```markdown
# Сверка с ТЗ — <дата>, <коммит>
Область: …   Проверено: N требований   Не проверено: …

## Сводка
| Вердикт | Кол-во |   …

## Находки (по убыванию серьёзности)
### [High] AUC-07 Ставка в 18:00 отклоняется — partial
ТЗ: «с 18:00 новые ставки отклоняются» (tz.md, «Расписание»)
Код: apps/api/src/modules/auctions/bids.service.ts:88 проверяет `now < endsAt` ✔
Обход: WebSocket-хендлер bids.gateway.ts:41 вызывает repository напрямую, без проверки времени ✘
Тест: нет теста для WS-пути
Действие: …

## Полный реестр
| ID | Требование | Вердикт | Доказательство | Тест |

## Поведение вне ТЗ
## Вопросы к заказчику (undecidable)
```

Не ставь `implemented` по названию функции или комментарию — только по прочитанному коду и тесту.
