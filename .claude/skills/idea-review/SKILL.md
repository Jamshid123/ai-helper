# Цепочка ревью идеи: продакт → UX → риск → разработчик → решение владельца

Решение 16.11.2026: новые идеи и изменения существующего поведения проходят четыре **независимых**
ревью. Решает владелец (заказчик), а не агент. Агент готовит бриф, собирает ревью и сводку,
не подталкивая к своему варианту.

## Когда не нужно

Исправление явного бага, опечатки, рефакторинг без изменения поведения, правки документации —
делаются по `AGENTS.md` без цепочки.

## Шаг 1. Бриф (одинаковый для всех)

Пять коротких блоков, только факты:
1. **Идея** — что предлагается, одной-двумя фразами (словами владельца).
2. **Зачем** — какую проблему решаем, для кого.
3. **Что есть сейчас** — как это работает сегодня (файлы/экраны/решения из `docs/PROJECT_CONTEXT.md` §8), что уже умеет система, чего нет (например: «SMS-провайдер не выбран, push не сделан»).
4. **Ограничения** — сроки, деньги, принятые решения, которые нельзя нарушить.
5. **Вопросы к ревьюерам** — если владелец хочет мнение о конкретном.

Бриф сохраняется в `docs/reviews/ideas/<ГГГГ-ММ-ДД>-<тема>.md` (туда же потом ревью, сводка и решение).

## Шаг 2. Четыре ревью — независимо

| Порядок в сводке | Роль | Скилл | Смотрит |
|---|---|---|---|
| 1 | Продакт | `product` | проблема, метрика, минимальный тест, текст для людей, развитие |
| 2 | UX-дизайнер | `ux-review` | путь пользователя, понятность, экраны и тексты, доступность, телефон и десктоп |
| 3 | Риск-аналитик | `risk-review` | фрод и злоупотребления, деньги, право, операционка, репутация |
| 4 | Разработчик | `backend` + `frontend` + `testing` | как сделать в текущем коде, объём (дни), что затронет, миграции, тесты, что может сломаться |

**Независимость обязательна:** каждый ревьюер получает только бриф и свой скилл, не видит ответы
других и не знает, что «склоняется» агент.
- Claude Code: четыре подагента параллельно (по одному на роль), каждому — бриф целиком + «прочитай `.claude/skills/<скилл>/SKILL.md` и ответь строго в его формате; код не меняй».
- Codex и другие инструменты без подагентов: роли по очереди; каждое ревью пиши в файл сразу и **не перечитывай предыдущие** до сводки.
- Ревьюеры только читают: никаких правок кода и коммитов.

Формат UX-ревью и ревью разработчика (у продакта и риск-аналитика — в их скиллах):
```
### UX-дизайнер
Вердикт: ЗА / ЗА С УСЛОВИЯМИ / ПРОТИВ
Путь пользователя (шаги): …
Что непонятно или неудобно: …
Предложения (экраны/тексты RU и UZ): …

### Разработчик
Вердикт: ЗА / ЗА С УСЛОВИЯМИ / ПРОТИВ
Как сделать (модули, файлы): …
Объём: … дней · Миграция БД: да/нет · Новые зависимости: …
Что может сломаться и как проверим (тесты): …
Что проще сделать первым шагом: …
```

## Шаг 3. Сводка для владельца

Без собственного решения агента:
1. Таблица: роль · вердикт · главное условие.
2. **В чём согласны** все четверо.
3. **Где расходятся** — по пунктам, кто что предлагает и почему.
4. **Варианты** (2–3): что входит, срок, главный плюс и главный риск каждого. Если все «ЗА» — один вариант и список условий.
5. Вопросы, на которые должен ответить владелец (по одному на развилку).

Владельцу показывается сводка + ссылка на полный файл. Спросить можно через выбор вариантов (AskUserQuestion), но формулировки — из сводки, без рекомендаций агента, если владелец их не просил.

## Шаг 4. После решения

- Решение — строкой в `docs/PROJECT_CONTEXT.md` → «Решения» (дата, что решено, что отклонено) и в конец файла ревью.
- Реализация — по `AGENTS.md` (ветка → проверки → PR). Условия ревьюеров, принятые владельцем, — в чек-лист PR.
