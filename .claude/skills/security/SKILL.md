# Security

Принципы взяты из OWASP ASVS / API Security Top 10 и подхода «insecure defaults» (Trail of Bits): **отсутствие конфигурации должно означать отказ, а не открытый доступ**.

## Обязательные меры проекта

**Секреты**
- Только в GitHub Actions Secrets (CI) и в `/opt/auksion/.env` на сервере (`chmod 600`, владелец — deploy-пользователь). В git — только `.env.example` без значений.
- Конфиг валидируется zod при старте; нет переменной → приложение не стартует. Запрещены фолбэки вида `process.env.JWT_SECRET ?? 'dev'`.
- В CI — сканер секретов (gitleaks) на каждом PR/пуше.
- Секреты не логируются, не возвращаются в ответах, не попадают в ошибки. pino с `redact` для `authorization`, `cookie`, `password`, `token`, `initData`, `phone`, `imei`.

**Аутентификация**
- Mini App: подпись `initData` проверяется на сервере (HMAC от bot token), `auth_date` не старше 1 часа. Только после этого — своя сессия.
- Сессии: access JWT 15 мин (HS256 с секретом ≥ 32 байт или EdDSA), refresh с ротацией и отзывом. Админка — httpOnly + Secure + SameSite=Strict cookie, CSRF-токен.
- Админка: пароль (argon2id, ≥ 12 символов); блокировка после 5 неудачных попыток на 15 мин; сессия админки ≤ 8 ч. Второй фактор (TOTP) отключён решением заказчика 14.11.2026 (ТЗ требует MFA — риск принят заказчиком); не возвращать без его решения.
- Телефон принимается только из `message.contact` бота, где `contact.user_id === from.id`.

**Авторизация**
- Deny by default: глобальный guard требует аутентификацию; публичные эндпоинты помечаются явно `@Public()`.
- RBAC по ролям из `PROJECT_CONTEXT.md` §2, проверка на сервере на каждом действии. UI-скрытие кнопок — не защита.
- Проверка владения объектом (IDOR): пользователь видит только свои допуски, заказы, коды выдачи.
- Конфликт интересов: продавец и сотрудники с доступом не ставят на свои лоты (проверка в транзакции ставки).

**Персональные данные**
- Минимизация: храним только нужное по ТЗ.
- Полный IMEI, паспортные/регистрационные данные, реквизиты выплат — шифрование на уровне приложения (AES-256-GCM, ключ из env, поле хранит `keyVersion`). Поиск по IMEI — по HMAC-хэшу.
- Публично — только «Имя Ф.» или псевдоним. Полное ФИО/телефон — только ролям с правом, каждое чтение → `audit_log`.
- Документы и фото актов — приватное хранилище, доступ через короткоживущие подписанные URL после проверки прав. Публичные фото лотов — отдельный бакет/каталог.
- Логи не содержат ПДн (маскирование телефона `+998*****0001`).

**Платежи**
- Вебхук: проверка подписи провайдера, сверка суммы/валюты/ID заказа, идемпотентность по `providerTxId`. IP allowlist провайдера — дополнительно, если он его публикует.
- Сумма заказа всегда считается на сервере, никогда не берётся из запроса клиента.

**Входные данные и API**
- Валидация всех входов (zod/class-validator, `whitelist: true, forbidNonWhitelisted: true`).
- Только параметризованные запросы. `$queryRawUnsafe` запрещён.
- Rate limit (Redis): запросы контакта/OTP, вход в админку, ставки (на пользователя и на лот), создание заказов.
- CORS — явный список: `https://auksion.expertly.uz` и домен админки. Никогда `*` с credentials.
- Заголовки: Helmet, HSTS. CSP для Mini App должен разрешать встраивание в Telegram Web: `frame-ancestors https://web.telegram.org https://*.telegram.org`. Для админки — `frame-ancestors 'none'`.
- Загрузка файлов: проверка MIME по сигнатуре, лимит размера, перекодирование изображений (sharp), удаление EXIF.
- Ошибки наружу — без стектрейсов и SQL; детали — только в логах.

**Аудит**
- Таблица `audit_log` только на вставку (у роли приложения нет UPDATE/DELETE на неё): кто, что, когда, над чем, причина, IP.
- Логируются: изменения лотов/расписания, акты, решения по рискам и спорам, баны и их снятие, возвраты, выдачи, просмотр ПДн/документов, входы в админку.

**Инфраструктура** (подробно — скилл `deploy`)
- SSH только по ключу, без root-входа; firewall: открыты 22/80/443.
- PostgreSQL и Redis не слушают публичный интерфейс. Отдельная БД и пользователь приложения с минимальными правами.
- Контейнеры не от root, read-only FS где возможно, без `--privileged`.
- Бэкапы БД шифруются и хранятся вне сервера; восстановление проверяется.

**Зависимости и CI**
- Lockfile обязателен, `pnpm install --frozen-lockfile`. Dependabot/Renovate + `pnpm audit --prod` в CI.
- GitHub Actions: сторонние actions закреплены по SHA, `permissions:` минимальные, никаких `pull_request_target` с чекаутом кода PR, деплой-секреты только в environment `production`.

## Чек-лист insecure defaults (прогонять на каждом ревью)

| Категория | Ищем | Плохо | Хорошо |
|---|---|---|---|
| Фолбэк-секреты | `?? '...'`, `|| 'secret'` для ключей | `JWT_SECRET ?? 'dev'` | обязательная переменная в zod-схеме |
| Fail-open флаги | флаги, отключающие защиту по умолчанию | `REQUIRE_MFA ?? 'false'` | защита включена без конфигурации |
| Дефолтные учётки | сиды `admin/admin` | сид с паролем в коде | первый админ создаётся CLI-командой с паролем из stdin |
| Слабая крипта | md5/sha1 для паролей, `Math.random` для кодов | `Math.random()` для кода выдачи | `crypto.randomInt`, argon2id |
| Широкий доступ | CORS `*`, публичные бакеты, `0.0.0.0` у БД | `origin: '*'` | whitelist доменов |
| Debug-утечки | стектрейсы в ответе, Swagger в проде без защиты | `/docs` открыт в проде | Swagger выключен или за авторизацией админа |

## Ревью безопасности диффа (перед пушем)

1. `git diff main...HEAD` — пройти по каждому файлу.
2. Для каждого нового эндпоинта: кто может вызвать? проверены ли роль и владение? валидирован ли вход? что утекает в ответ?
3. Для каждого изменения env/конфига: какой дефолт, если переменной нет?
4. Прогнать таблицу insecure defaults и `gitleaks detect`.
5. Находку подтверждать конкретным путём эксплуатации (кто, какой запрос, что получит). Без пути — пометка «требует проверки», а не «уязвимость».
