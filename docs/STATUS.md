## В работе
- Backend по `docs/plans/backend-mvp.md` — ведётся в основной сессии (ночная задача на паузе: у её запусков нет прав на push в репозиторий).
  - Этап 1, шаг 1 ✓: `apps/api` (NestJS + Fastify + Prisma), конфиг на zod, `/api/v1/health` (БД + Redis), логи с redact, Docker-образ, сервисы `api`/`redis` в compose, CI с Postgres/Redis.
  - Этап 1, шаг 2 ✓: схема БД домена (User, Restriction, Lot, Admission, Bid, Order, Obligation, OutboxEvent, AuditLog, Setting) + миграция с CHECK-ограничениями; тесты гарантий схемы.
  - Этап 2.4 (ядро торгов) ✓: `BidsService.placeBid` — транзакция + `FOR UPDATE`, идемпотентность (в т.ч. гонка одинаковых ключей), допуск, окно торгов, статус, ограничение, мин. цена по правилам ТЗ, монотонный `seq`, событие в outbox. 10 тестов сценариев приёмки (одновременные предложения, 17:59:59/18:00:00, повтор ключа и др.).
  - Этап 2.1 (вход) ✓: проверка подписи `initData` (HMAC, ≤ 1 ч, timing-safe), `POST /api/v1/auth/telegram` → покупатель (upsert по telegramId, публичное имя «Имя Ф.» / «Участник NNNN») + сессия JWT 1 ч; глобальный guard (всё закрыто, кроме `@Public`), `GET /api/v1/auth/me`. `JWT_SECRET` генерируется на сервере при выкладке.
  - Этап 2.2 + HTTP предложений ✓: `GET /api/v1/lots`, `/lots/:id`, `/schedule` (публично, формат = контракт Mini App), `POST /api/v1/lots/:id/bids` (авторизация, zod-валидация суммы строкой и uuid-ключа, отказы → код + текст + minBid).
  - Этап 2.3 (допуск) ✓: `POST /api/v1/lots/:id/admission` (правила обязательны, сумма = взнос лота, неоплаченный заказ переиспользуется), `GET /api/v1/me/admissions`, `PaymentsService.confirmAdmissionPayment` (блокировка заказа, сверка суммы, повторы → no-op, поздняя и двойная оплата → возврат, аудит), провайдеры Disabled/Fake, `POST /payments/fake/:orderId/complete` только при `PAYMENTS_MODE=fake`.
  - Этап 2.5 (расписание) ✓: `LotLifecycleService` (открытие по `opensAt`, закрытие ровно один раз: победитель — максимум суммы, при равенстве — раньше; обязательство rank 1 с 30% и сроком 15 мин; без предложений — без продажи) + `LifecycleScheduler` (sweep каждые 5 с под advisory-блокировкой PostgreSQL).
  - Автопредложение до максимума ✓ (решение заказчика 13.11): API + запуск в 09:00.
  - Mini App: автопредложение ✓ (демо).
  - Напоминание о начале ✓ (API + Mini App демо); отправку через бота подключит модуль уведомлений (outbox → Telegram).
  - Судьба взноса — на паузе до ответа религиозной экспертизы (решение заказчика 13.11).
  - Модель Halal: подтверждение покупки (15 мин → 30% за 2 ч) ✓; депозит — решение по хранению отложено.
  - Следующий шаг: затем выкуп — предоплата 30%/остаток, истечение 15 мин/24 ч, следующий участник, бан 50 дней, код выдачи.

## Очередь (заказчик 14.11.2026)
1. Выложить Mini App ↔ API в демо + тестовые лоты.
2. Регистрация по-настоящему: имя → «Поделиться контактом» через бота → правила (план 2.10).
3. Админка: вход сотрудника (пароль + TOTP) → категории (ru/uz, вкл/выкл) → товары → лоты из товаров → участники (ограничение/снятие, отмена допуска с возвратом).
4. Выход из лота до начала торгов с возвратом 100% (план 2.11).
5. Затем выкуп (15 мин → 30% → 70%, следующий участник, ограничения).

## Вопросы к заказчику
- Решения из `docs/research/market-and-risks.md` §4: автопредложение до максимума, судьба взноса (зачёт/бонус), бесплатный первый допуск и рефералы, узбекский на кириллице, срок предоплаты 15 мин, лимит выигрышей.
- Подтверждённый телефон как условие допуска (ТЗ «Аккаунт покупателя»): включу вместе с приёмом контакта через бота; до этого допуск требует только принятия правил.
- Лидер не может перебить собственное предложение (защита от «разгона» цены; ТЗ прямо не говорит) — выбран безопасный вариант, подтвердите.
- Конфликт интересов «сотрудник ставит на лоты пилота»: сотрудники — отдельные учётки админки; связать их с Telegram-аккаунтами покупателей для запрета — нужно правило (например, список запрещённых telegramId).
