# AuksionGO — Project Context

> Статус: **v0.2** — стек подтверждён заказчиком 13.11.2026. Кода ещё нет.
> Эталон требований: [`docs/spec/tz.md`](spec/tz.md). При изменении архитектуры этот файл обновляется в том же коммите.

## 1. Что строим (в двух абзацах)

Площадка еженедельных **английских аукционов** (цена только растёт) для Узбекистана. Одна торговая сессия в неделю — **пятница 09:00–18:00 Asia/Tashkent**, все лоты недели торгуются в этом окне, без продлений. На пилоте продавец — сама площадка (телефоны: «Новые» / «Б/у»), внешние продавцы включаются флагом позже.

Монетизация: покупатель платит **взнос за допуск к конкретному лоту** (~$1 в сумах), затем ставит. Победитель за **15 мин** вносит **30% предоплаты**, затем за **24 ч** доплачивает остаток и забирает товар в пункте выдачи по одноразовому коду. Неоплата → предложение следующему по ставке (без переторжки) + бан ставок на **50 дней**.

Первый клиент — **Telegram Mini App**. Android/iOS подключаются позже к тому же API.

## 4. Критичные инварианты (обязательно покрыть тестами)

1. Ставка принимается только: есть допуск, лот `LIVE`, `server_now < 18:00`, сумма ≥ `current + step` (первая ≥ `start`), нет конфликта интересов, нет активного бана.
2. Ставка пишется в транзакции с блокировкой строки лота (`SELECT … FOR UPDATE`); порядковый номер монотонный; при равных — выигрывает первая записанная.
3. Идемпотентность: повтор запроса ставки с тем же ключом, повтор вебхука оплаты, повтор закрытия лота — **без дублей**.
4. Закрытие лота выполняется ровно один раз и создаёт ровно одно обязательство оплаты.
5. Сотрудник не может изменить ставку или назначить победителя.
6. Все даты в БД — UTC; календарь и дедлайны — Asia/Tashkent; таймеры считает сервер.
7. Деньги — целые сумы (`bigint`), никакого float.
8. Полный IMEI, ФИО, документы — только для ролей с правом, каждое чтение — в аудит.

## 5. Стек

Принцип: один язык (TypeScript) на всё, минимум движущихся частей, один сервер.

| Слой | Выбор | Почему |
|---|---|---|
| Монорепо | pnpm workspaces | Общие типы/валидация между API и клиентами без лишних инструментов |
| Backend | Node.js 22 LTS + **NestJS 11** + Fastify adapter (CommonJS; переход на ESM — до TypeScript 7) | Модули, guards (RBAC), DI из коробки; зрелый, легко масштабировать команду |
| ORM / миграции | **Prisma 6** (+ raw SQL для блокировок ставок) | Типобезопасность, понятные миграции |
| БД | **PostgreSQL** — уже установлен на сервере (вне Docker), отдельная БД `auksion` | Транзакции, row locks, надёжность денег |
| Кэш / очереди / pub-sub | **Redis 7** + BullMQ | Отложенные задачи (открытие 09:00, закрытие 18:00, таймеры 15 мин / 24 ч), fan-out WebSocket |
| Real-time | WebSocket (Socket.IO + Redis adapter) | Комнаты лотов, ресинк состояния после переподключения |
| Mini App | **React 19 + Vite + TypeScript**, `@telegram-apps/sdk-react`, TanStack Query, i18next (ru/uz) | Стандарт для Telegram Mini Apps |
| Админка | React + Vite + shadcn/ui на основе шаблона shadcn-admin (отдельное приложение, отдельный домен/путь, MFA) | Изоляция от публичного клиента, готовые таблицы/формы |
| Mobile (позже) | React Native (Expo) | Переиспользование TS-типов и API-клиента |
| Валидация контрактов | zod + OpenAPI из NestJS | Один контракт для Mini App, админки и мобайла |
| Тесты | Vitest (unit; для API — через SWC ради decorator metadata), интеграционные — на настоящих Postgres/Redis (в CI — service-контейнеры), Playwright (e2e) | Инварианты аукциона проверяются на реальной БД |
| Инфра | Docker Compose на одном VPS (Европа), reverse proxy с TLS (Caddy или существующий на сервере), GitHub Actions → GHCR → SSH deploy | Просто, быстро, без Kubernetes на пилоте |
| Наблюдаемость | pino-логи (JSON), healthchecks, Sentry (опционально) | |
| Бэкапы | ежедневный `pg_dump` + шифрование + вынос за пределы сервера | |

## 7. Безопасность (базовые требования)

- Секреты только в GitHub Secrets / `.env` на сервере (не в git); `.env.example` без значений.
- Проверка подписи Telegram `initData` (HMAC) на каждом запросе Mini App + проверка `auth_date`.
- Вебхуки платёжки — проверка подписи + сверка суммы/валюты/ID + запрос статуса.
- Rate limit на OTP и ставки; CORS только на свои домены; Helmet/CSP.
- Админка: MFA (TOTP), RBAC по ролям из §2, аудит всех изменений и чтений чувствительных данных.
- Чувствительные поля (IMEI, паспортные данные) — шифрование на уровне приложения; медиа документов — приватное хранилище с подписанными ссылками.
- Сервер: SSH только по ключу, firewall (22/80/443), автообновления безопасности, Postgres/Redis не торчат наружу.
- Зависимости: lockfile, `pnpm audit`/Dependabot, сканирование секретов в CI.

## 11. Сервер (осмотр 13.11.2026, только чтение)

- Ubuntu 24.04, 6 CPU, 11 ГБ RAM (свободно ~9), диск 88 ГБ свободно. Docker 29.5 + Compose v5.
- Reverse proxy — **nginx на хосте** (80/443), сертификаты Let's Encrypt в `/etc/letsencrypt/live`. Уже обслуживает: m-pulim.uz (+api, payment), n8n / tg-helper / karnaychi-api / pyrus-master / ai-helper `.expertly.uz`. Мы добавляем свои vhost-файлы, чужие не трогаем.
- PostgreSQL — Docker-контейнер `ai-helper-postgres` (postgres:16, `127.0.0.1:5432`, создан 12.05.2026 вручную, не compose). Внутри — БД другого проекта `ai_helper_agent` (45 МБ), единственный пользователь `ai_helper_user` (superuser). Отдельного Postgres на хосте нет.
- MySQL 8.0 на хосте — базы проекта m-pulim (`pulim_app`, `pulim_db`); пользователь `pulim@%` допускает вход с любого адреса, а порт 3306 открыт в интернет.
- Занятые порты: 22, 80, 443, 3000, 3030, 3100, 3111, 3306, 33060, 5432, 5678, 8088, 8787–8790, 18080. Для AuksionGO резервируем `127.0.0.1:3400–3409`.
- Найденные риски (касаются всего сервера, без согласия не меняем): MySQL 3306/33060 и n8n 5678 открыты в интернет; firewall `ufw` выключен; вход root по паролю разрешён; fail2ban не установлен.
