# AGENTS.md — правила работы в репозитории AuksionGO

Единый источник правил для всех, кто меняет репозиторий: людей и AI-агентов (Codex читает этот файл,
Claude Code подключает его из `CLAUDE.md`). Меняешь правила — меняй здесь.

Перед любой задачей (порядок важен — экономит контекст, см. скилл `token-economy`):
1. `docs/STATUS.md` — где мы сейчас и следующий шаг.
2. `docs/CODEMAP.md` — где что лежит в коде.
3. Нужный раздел `docs/PROJECT_CONTEXT.md` (архитектура, инварианты, решения) и `docs/spec/tz.md` (ТЗ).
4. Нужный скилл (таблица ниже). Не перечитывай весь репозиторий.

Установка, локальные БД и команды — `README.md`. Процесс (ветки, PR, проверки) — `CONTRIBUTING.md`.

## Скиллы

Лежат в `.agents/skills/<name>/SKILL.md` (Codex) — это ссылки на `.claude/skills/<name>/` (Claude Code),
файлы одни и те же. Новый скилл: папка в `.claude/skills/` + ссылка `ln -s ../../.claude/skills/<name> .agents/skills/<name>`
(CI проверяет, что ссылки есть у всех).

| Задача | Скилл |
|---|---|
| API, БД, торги, платежи, фоновые задачи | `backend` |
| Сайт покупателя (`apps/miniapp`) и админка | `frontend` |
| Android/iOS (Expo) | `mobile` |
| Тесты любого уровня, TDD | `testing` |
| Секреты, авторизация, персональные данные, ревью безопасности | `security` |
| Docker, CI/CD, сервер, выкладка | `deploy` |
| Сверка реализации с ТЗ | `spec-check` |
| Начало задачи, поиск по коду, экономия контекста | `token-economy` |
| Ревью UI/UX экранов, «сделай удобнее» | `ux-review` |
| Что строить и зачем: идея, правила, запуск, рост, тексты для пользователей | `product` |
| Фрод, злоупотребления, денежные, правовые и операционные риски идеи | `risk-review` |
| Вопросы об исламе; халяльность денежных правил и механики (ханафитский мазхаб) — образовательный разбор, не фетва | `hanafi-advisor` |
| **Новая идея или изменение поведения продукта** — четыре независимых ревью и решение владельца | `idea-review` |

## Принципы

- **Без over-engineering.** Модульный монолит, один сервер, ничего «на вырост» без запроса. Новая зависимость — только если без неё заметно хуже; обоснование в описании коммита.
- **Не фантазировать.** Если ТЗ молчит или противоречит — спроси владельца задачи, не додумывай бизнес-правила. Решённые вопросы фиксируй в `docs/PROJECT_CONTEXT.md` → «Решения» (решения новее ТЗ: при расхождении действует решение).
- **Безопасность по умолчанию.** Секреты никогда не попадают в git, логи или ответы API. Отсутствие конфигурации = отказ в доступе, а не «открыто». Не читай `.env`, ключи и дампы.
- **Доказательства, а не уверенность.** Перед словами «готово/работает/тесты проходят» — запусти команду и посмотри вывод.

## Процесс изменений (обязательно, решение 16.11.2026 — работаем вдвоём через `main` + PR)

0. **Новая идея или изменение поведения продукта** (правила торгов, деньги, уведомления, экраны, акции) — сначала цепочка `idea-review`: продакт, UX-дизайнер, риск-аналитик и разработчик независимо, решает владелец. Без решения владельца такую задачу не реализуем. Баги, опечатки, рефакторинг и документация — без цепочки.

1. **Ветки.** `main` — то, что работает на сервере; напрямую в `main` не пушим. Каждая задача — своя ветка от свежего `main`:
   `claude/<тема>` (Claude Code), `codex/<тема>` (Codex), `<имя>/<тема>` (человек). Чужие ветки не переписываем.
   Коммиты — Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`), по-английски, кратко и по делу.
2. **До PR:**
   - подтяни `main` (`git fetch origin main && git rebase origin/main`) и реши конфликты;
   - запусти lint, typecheck и тесты затронутых пакетов (команды — `README.md`); при изменении UI — проверь в браузере;
   - новый или изменённый сценарий сайта, исправленный баг в нём — сквозной тест в `apps/e2e` (Playwright) в том же PR (решение 17.11.2026: регрессия ведётся вместе с кодом);
   - запись в `CHANGELOG.md` (раздел `[Unreleased]`, формат Keep a Changelog);
   - изменились архитектура, стек, модули, схема БД, инфраструктура или переменные окружения — обнови `docs/PROJECT_CONTEXT.md` (и `.env.example`) в том же PR;
   - обнови `docs/STATUS.md`, а при изменении структуры кода — `docs/CODEMAP.md`.
3. **PR и мерж без вопроса** (решение владельца 16.11.2026). Если lint, typecheck, тесты и сборка зелёные, ошибок нет и поведение проверено — пушь свою ветку и открывай PR в `main` по шаблону (`.github/pull_request_template.md`), без согласования. Когда CI по PR зелёный на последнем коммите и конфликтов с `main` нет — агент **сам мержит свой PR** (merge commit) и проверяет выкладку. Чужие PR агент не мержит. Не мержим, если есть непрочитанные комментарии ревьюера, открытый вопрос владельцу (например, бизнес-правило из `idea-review` ещё не решено) или PR помечен «не мержить».
4. **Выкладка — два стенда** (решение владельца 17.11.2026). Мерж в `main` = автоматическая выкладка на **dev** (`dev.auksiongo.uz`, workflow «Deploy dev»: CI → сборка → сервер → проверка здоровья → откат при сбое); ручной запуск — только с `main`, агенту можно без вопроса. **Прод** (`auksiongo.uz`) — только workflow «Deploy prod» и **только с явного «да» владельца** (environment `production`, подтверждает владелец); агент сам прод не выкладывает и не запускает. Настройка доменов («Server domains») — тоже с «да» владельца. После выкладки — короткий отчёт: что выложено, как проверено, риски.
5. **Нужно явное «да» человека:** выкладка в прод, удаление данных и необратимые операции на сервере, смена секретов, workflow, которые пишут в прод-БД (`admin-create`, `staff-set-phone`, `demo-*`), force-push в общие ветки. Ручные правки ставок/победителя запрещены ТЗ — никогда.
6. Если что-то красное, не проверено или есть сомнение в бизнес-правиле — не открывай PR «на авось»: спроси.

## Чего не делать

- Не коммитить `.env`, ключи, дампы БД, реальные персональные данные (даже в тестах/фикстурах).
- Не отключать и не пропускать тесты ради зелёного CI.
- Не править ставки/победителя «руками» ни в коде, ни в админке — это запрещено ТЗ.
- Не использовать `float` для денег — только целые сумы (`bigint`).
- Не трогать чужие проекты на сервере (он общий).
- В интерфейсе покупателя не «ставка», а «предложить цену».
